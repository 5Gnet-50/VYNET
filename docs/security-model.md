# نموذج الأمن

## الحماية المهيأة في المصدر

- Supabase SSR cookie client خادمي و`proxy.ts` لتحديث الجلسة عبر `auth.getClaims()`.
- كوكيز الجلسة مضبوطة `HttpOnly` و`SameSite=Lax` و`Secure` في الإنتاج لأن المشروع لا يستخدم عميل Supabase في المتصفح.
- سياسات القراءة للوكلاء تتطلب عضوية AGENT حالية ووكيلًا نشطًا؛ روابط العميل/البطاقة/البيع/التسليم مقيدة بقيم organization مركبة. RPC تسجيل الحدث يسمح حاليًا بـ`LOGIN_SUCCESS` فقط لتقليل تزوير أحداث تغيير كلمة المرور/إلغاء الجلسة.
- Server Action للاستيراد تتحقق من الجلسة وعضوية OWNER/ADMIN باستخدام جلسة Supabase، ثم تعالج CSV وتولد fingerprint والتشفير بالخادم. RPC إنشاء الدفعة لا تنفذ إلا عبر مفتاح خدمة server-only. لا يرسل النموذج بصمة أو ciphertext مشتقًا.
- قراءة credential المباشرة عبر RPC ما زالت مسحوبة من أدوار التطبيق؛ لا يوجد مسار reveal خادمي.
- RPC Bootstrap لمرة واحدة تنشئ Organization وعضوية OWNER لمستخدم profile موجود؛ التنفيذ محصور بـservice_role، ويرفض إذا وجدت منظمة أو عضوية OWNER سابقة.
- التسجيل العام trigger ينشئ profile وCustomer غير مفعل فقط. لا توجد grants أو policies لتعديل memberships مباشرة.
- RPC انتهاء التحويل متاحة لـOwner/Admin للمنظمة فقط، مع قفل صفوف والتحقق من الحجز قبل تحريره.
- Server Actions للحساب تتحقق من المدخلات وتستخدم mapping الهاتف نفسه في التسجيل والدخول؛ رسائل فشل الدخول عامة.
- تشفير AES-256-GCM مع IV عشوائي 12 بايت ومفتاح مستقل؛ HMAC-SHA256 منفصل ومقيد بالمنظمة لمنع التكرار.
- migrations تهيئ RLS، وتحد قراءة Cards بحيث لا تشمل أعمدة ciphertext. دوال التغيير المرشحة تستخدم `search_path` فارغًا وتتحقق من الأدوار والنطاق؛ لم تُطبق أو تُختبر.
- لا أسرار فعلية أو service-role key في المصدر؛ `.env*` مستثنى عدا المثال.

## غير متحقق / مخاطر

- لا إعداد Supabase ولا تطبيق migrations ولا اختبار RLS؛ التفويض غير مثبت.
- Bootstrap موجود في SQL لكنه غير منفذ على Supabase؛ يحتاج مستخدمًا موجودًا وUUID صحيحًا عند تشغيله الإداري.
- لا سجل لمحاولات دخول فاشلة؛ يحتاج مسارًا آمنًا لتسجيل مستخدم مجهول.
- حدث `LOGIN_SUCCESS` ما زال قابلًا للاستدعاء مباشرة من مستخدم مصادق لتسجيل حدث على حسابه؛ لا يُعد مصدر تدقيق مقاومًا للتزوير أو بديلًا عن سجل Auth الموثوق. لا توجد rate limits.
- تسوية التحويلات لا تعمل تلقائيًا بجدولة؛ يجب استدعاء RPC من Owner/Admin. لا توجد سياسة تنظيف لـidempotency rows.
- مفاتيح التشفير ودورانها واستعادتها غير معدة. فقد مفتاح التشفير يمنع استعادة الأسرار.
- لا rate limiting أو إدارة revocation فعلية أو فحص رفع خادمي للملفات.
- `@supabase/ssr` مقفل على إصدار 0.x؛ راجع توافقه وتغييره قبل النشر.
- لا تكشف credentials في logs/URLs/errors/localStorage أو التحليلات. يلزم تدقيق RLS وSECURITY DEFINER مستقل قبل إدخال بيانات حقيقية.

**حد الثقة في الاستيراد:** Server Action الجديدة تحسب HMAC والتشفير بعد تحقق الجلسة والعضوية. المفتاح الخادمي يستدعي RPC محمية عن authenticated. أي تسريب لمفتاح الخدمة يسمح بتجاوز الثقة هذه، لذا لا يمكن اختباره أو تفعيله حتى إعداد secret manager/بيئة اختبار آمنة. لم يُختبر المسار على Supabase.

وبالمثل، RPC قراءة ciphertext الخاص بالبطاقة لم يعد قابلًا للاستدعاء من أدوار التطبيق؛ لا يوجد مسار Server Action يفك التشفير بعد التحقق ويسجل الكشف. لا تعرض ciphertext أو credential مباشرة.
