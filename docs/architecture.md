# المعمارية والحالة الفعلية

تطبيق Modular Monolith على Next.js App Router، دون خدمة منفصلة. هذا وصف الكود والمخطط المقترح، لا ادعاء أن backend مهيأ.

## الطبقات

- `src/app`: Routes وServer Actions للحساب. تهيئة Supabase تعتمد على متغيرات بيئة.
- `src/components`: RTL UI؛ الصفحات التشغيلية الحالية placeholders معلنة ولا تستخدم بيانات وهمية.
- `src/lib/domain`: قواعد نقية قابلة للاختبار (الهوية، انتقال البطاقة، FIFO، والتحقق من بنود طلب التحويل متعدد الفئات).
- `src/lib/auth`: قراءة جلسة Supabase والعضويات لتحديد مساحة VYNET؛ صفحات الإدارة والوكيل تحرس صلاحية الدور من الخادم.
- `src/lib/imports`: محلل CSV. بياناته السرية يجب أن تبقى في server process.
- `src/lib/security`: تشفير AES-256-GCM وبصمة HMAC.
- `src/lib/supabase`: عميل SSR خادمي وقراءة الإعداد.
- `src/types`: نماذج المجال؛ Card لا يحتوي حقول الاعتماد السرية.
- `supabase/migrations`: migrations مرشحة لطلبات التحويل ومراجعتها وتنفيذها، أسعار الوكيل حسب الشبكة والمنتج، snapshots مالية، التنبيهات وRLS/RPCs. لم تطبق أو تختبر على PostgreSQL/Supabase.

## حدود الثقة

المتصفح ليس مصدرًا موثوقًا. عند تفعيل backend، كل endpoint يجب أن يتحقق من session والعضوية ودور المستخدم ونطاق المنظمة وحالة المورد. عمليات البيع والتحويل والاعتماد تحتاج معاملة DB وقفلًا مناسبًا ومفتاح idempotency. RLS دفاع إضافي ويجب اختبار عزل العملاء والوكلاء والمنظمات على PostgreSQL قبل التشغيل.

## مسار البيانات الحساس

CSV يُحلل في الخادم، وتشفّر credentials قبل التخزين. لا تمرر نتيجة `parseCardCsv` للعميل لأنها قد تحمل credentials الصحيحة حتى للصفوف المكررة. لا تمنح قراءة مباشرة لأعمدة ciphertext. كشف credential يمر بإجراء مصرح ومسجل. لا أسرار في URLs/logs/errors/analytics.

## حالة الخدمات

لا توجد بيانات اعتماد Supabase أو قاعدة اختبار أو تطبيق migrations. لا توجد واجهات تشغيل متكاملة لإدارة الأسعار أو التحويلات، ولا خدمات كاملة للاستيراد أو البيع أو التقارير. لا ترفع Production ولا تدعي وجود backup. راجع `decisions.md` و`mvp-scope.md`.
