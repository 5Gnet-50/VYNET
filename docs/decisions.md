# القرارات والفجوات

## BLOCKED قبل التشغيل

1. لا Supabase dev/test ولا URL/publishable key ولا مفاتيح تشفير؛ أدوات Supabase/Postgres/Docker غير متوفرة. لم تطبق أو تختبر migrations.
2. Owner اعتمد تهيئة أول Organization وOWNER عبر RPC إدارية أحادية الاستخدام، محصورة بـservice_role. لا ينشئ التسجيل العام Owner. التنفيذ يحتاج مشروع اختبار وUUID لمستخدم موجود.
3. مستخدم VYNET يدخل برقم الهاتف وكلمة المرور دون عرض بريد Auth. الهوية الداخلية `phone@vynet.app`. التسجيل العام معطل؛ trigger ينشئ profile فقط، أما العضويات والحسابات فتُنشأ إداريًا.
4. مفاتيح AES/HMAC يجب توفيرها وإدارتها ودورانها واستعادتها بأمان؛ لا توجد قيم هنا.
5. سجل Stage 1 المالي يحتفظ بمبالغ موجبة ونوع الحدث والعملة والعملية المرتبطة، دون فرض قاعدة debit/credit. العملة والسعر مصدرهما إعداد سعر الوكيل لكل شبكة/منتج، ويثبتان عند التنفيذ.

## افتراضات تقنية تحتاج مراجعة

- لا ينشئ تسجيل VYNET العام مستخدمين أو دور CUSTOMER. Customer/VY CARD منفصل عن هذه الواجهة.
- رمز التفعيل مصمم كـ192-bit أحادي الاستعمال، عشر دقائق؛ طريقة تسليمه للوكيل تحتاج تحققًا ميدانيًا.
- اعتماد الدفعة يمنع اعتمادها ما دامت فيها صفوف رفض/مراجعة/نقص. هذا خيار محافظ لكنه قرار سير عمل يحتاج اعتمادًا.
- بصمة التكرار HMAC مقيدة بالمنظمة؛ يتطلب مفتاحًا ثابتًا ومحميًا.
- FIFO مرتب بـcreated_at ثم UUID.
- التحويل المعلق صالح 24 ساعة. بعد ذلك يحرر مسار تسوية خادمي الحجز ويعلّم التحويل EXPIRED ويسجل Ledger/Audit. تكرار التسوية لا يكرر الحركة.
- duplicate fingerprint scope داخل Organization فقط، ومقيد ب unique constraint مركب.
- ملف CSV يعالج في Server Action بعد التحقق من العضوية. HMAC والتشفير server-side، واستدعاء RPC الإنشاء عبر service-role فقط.

أساس طلب التحويل والمراجعة والتنفيذ والقبول والسعر المثبت أضيف كمخططات RPC تزايدية. لم تُختبر migrations فعليًا، ولا توجد آلية داخلية آمنة لإنشاء الوكلاء والمديرين أو واجهات تشغيل الأسعار والتحويل. لا تنفذ Bootstrap قبل توفير Supabase test ومستخدم Owner الذي سيُربط بها.
