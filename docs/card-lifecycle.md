# دورة البطاقة

التدفق أدناه هو التصميم المرشح في SQL وليس دورة تشغيلية مثبتة.

1. أساس الاستيراد الحالي CSV عبر Server Action يتحقق من جلسة المستخدم وعضويته. المحلل ومفاتيح HMAC والتشفير server-only؛ لا ترجع الاعتمادات أو fingerprint للعميل. دعم مرجع PDF ومعالجة الملف غير منفذ.
2. RPC إنشاء Batch تستدعى من Server Action بواسطة service-role server-only، وتتحقق من دور actor في قاعدة البيانات ومن الشبكة/المنتج. لا يستطيع authenticated استدعاء RPC مباشرة. uniqueness لـ(organization_id, fingerprint) تمنع التكرار في المنظمة، وتسمح به بين المنظمات.
3. طلب الوكيل متعدد الفئات ينشئ طلبًا وبنودًا فقط ولا يحجز المخزون. RPC مراجعة المالك تستطيع قبول/تقليل/رفض البنود مع سبب الرفض وإشعار داخلي وسجل تدقيق.
4. RPC التنفيذ بعد الموافقة يخصص بطاقات فردية FIFO، يقفلها، يثبت سعر الوكيل والعملة لكل بند، ويكتب transfer lines وinventory movements وfinancial entries والتدقيق والتنبيهات في معاملة واحدة. لا يوجد سعر افتراضي؛ يفشل التنفيذ عند غياب سعر مهيأ أو مخزون كافٍ. migration الجديدة تسحب صلاحية RPC التحويل القديمة.
5. قبول الوكيل مربوط بالتحويل الجديد: بعد القبول تنتقل الحيازة إلى الوكيل وتُسجل الحركة والتدقيق والتنبيهات. انتهاء المهلة يعيد الحجز إلى مخزون المالك ويسجل عكسًا ماليًا مرتبطًا بقيد التحويل.
5. البيع مصمم لاختيار بطاقة FIFO بقفل صف، وإنشاء Sale/Item/Delivery/Ledger في معاملة واحدة.
6. التسليم لا يغير حالة الشبكة إلى USED. كشف الاعتماد يسجل حدثًا؛ التراجع يعيد البطاقة للمخزون فقط إن لم يكشف السر، وإلا COMPROMISED.
7. تفعيل العميل مصمم برمز أحادي الاستعمال، لا يتضمن بيانات البطاقة.

قراءة ciphertext RPC ما زالت محجوبة عن أدوار التطبيق؛ لا يوجد مسار reveal. مسار CSV متصل من Server Action إلى RPC موثوقة بالمفتاح الخادمي لكنه غير متحقق على Supabase. انتهاء التحويل لا يملك scheduler؛ التسوية يدوية من Owner/Admin عبر RPC.

قواعد FIFO وانتقالات الحالة ومطابقة مخطط RPC باختبارات وحدات نصية مشمولة. SQL غير مطبق وغير متحقق فعليًا على PostgreSQL؛ لا توجد واجهات تشغيل مكتملة لتهيئة الأسعار أو طلب/مراجعة/تنفيذ/قبول التحويل أو المخزون أو البيع أو الكشف أو التنبيهات.
