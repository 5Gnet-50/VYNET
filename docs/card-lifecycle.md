# دورة البطاقة

التدفق أدناه هو التصميم المرشح في SQL وليس دورة تشغيلية مثبتة.

1. Server Action تتحقق من جلسة المستخدم ودور OWNER/ADMIN، وتقبل CSV حتى 5MB/5000 صف. المحلل ومفاتيح HMAC والتشفير server-only؛ لا ترجع الاعتمادات أو fingerprint للعميل.
2. RPC إنشاء Batch تستدعى من Server Action بواسطة service-role server-only، وتتحقق من دور actor في قاعدة البيانات ومن الشبكة/المنتج. لا يستطيع authenticated استدعاء RPC مباشرة. uniqueness لـ(organization_id, fingerprint) تمنع التكرار في المنظمة، وتسمح به بين المنظمات.
3. اعتماد Batch مصمم لإنشاء بطاقات OWNER_STOCK وحركات ledger ذريًا، وبـidempotency.
4. إنشاء التحويل يحجز بطاقات FIFO لمدة 24 ساعة ويسجل انتقال العملية COMPLETED→RESERVED في ledger. قبول الوكيل قبل expires_at فقط ينقلها إلى AGENT_STOCK. بعد 24 ساعة Owner/Admin يستطيع تسوية التحويل: يفحص كل البطاقات، يعيدها إلى حالة العملية COMPLETED في OWNER_STOCK، ويسجل TRANSFER_EXPIRY وaudit، ثم يعلّم التحويل EXPIRED. القفل والحالة PENDING تجعل التكرار بلا أثر إضافي.
5. البيع مصمم لاختيار بطاقة FIFO بقفل صف، وإنشاء Sale/Item/Delivery/Ledger في معاملة واحدة.
6. التسليم لا يغير حالة الشبكة إلى USED. كشف الاعتماد يسجل حدثًا؛ التراجع يعيد البطاقة للمخزون فقط إن لم يكشف السر، وإلا COMPROMISED.
7. تفعيل العميل مصمم برمز أحادي الاستعمال، لا يتضمن بيانات البطاقة.

قراءة ciphertext RPC ما زالت محجوبة عن أدوار التطبيق؛ لا يوجد مسار reveal. مسار CSV متصل من Server Action إلى RPC موثوقة بالمفتاح الخادمي لكنه غير متحقق على Supabase. انتهاء التحويل لا يملك scheduler؛ التسوية يدوية من Owner/Admin عبر RPC.

قواعد FIFO وانتقالات الحالة وانتهاء التحويل مشمولة باختبارات وحدات نقية. SQL غير مطبق وغير متحقق على PostgreSQL؛ لا توجد واجهات تشغيل مكتملة للتحويل والبيع والكشف والتراجع.
